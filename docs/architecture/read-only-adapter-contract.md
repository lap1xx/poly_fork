# Контракт read-only адаптера букмекера и маршрутизация событий

> Статус: целевой контракт для backlog №4. Это описание архитектуры, а не изменение runtime-поведения. До реализации адаптеров и индексов необходимо сохранять текущий fail-closed matching, 1win priority и отдельную пару Polymarket ↔ одна выбранная БК.

## Цель и границы

Контракт нужен, чтобы подключать независимые источники котировок к общему потоку событийного пересчёта без полного обхода каталога на каждое обновление. Он не расширяет список источников и не меняет текущий выбор feeds. Любые данные остаются read-only.

Адаптеру запрещено обращаться к аккаунту или кошельку, получать баланс, создавать/изменять купон, резервировать сумму или размещать ставку. Наличие обычной ссылки на страницу события не даёт адаптеру права добавлять параметры купона или суммы.

## Обязательные инварианты

1. Один расчётный кандидат состоит ровно из двух ног: одна нога Polymarket и одна нога ровно одного bookmaker adapter.
2. Исходы должны быть противоположными для одного и того же бинарного события и периода. Нельзя соединять ставки из двух БК или две стороны Polymarket.
3. Тип рынка и период должны совпадать: например, победитель матча не эквивалентен победителю карты или сета. Неподдерживаемый тип и неоднозначная привязка отвергаются, а не угадываются.
4. Для пригодной пары нужны обе открытые, конечные и свежие котировки. Одна свежая сторона не делает пригодной всю пару.
5. Для свежести используется локальное время получения котировки адаптером. Время источника сохраняется как отдельные необязательные данные и не подменяет локальный receipt при отсутствии доверенной семантики.
6. Любой отказ адаптера, неполный каталог, неоднозначное событие или устаревшая цена закрывает путь к расчёту этой пары; кэш не превращается в подтверждение актуальной исполнимой цены.

## Объекты контракта

### Рынок Polymarket на входе

Нормализованный вход описывает одну binary market:

- `market_key` — стабильный ключ рынка (сейчас обычно PM slug);
- `event_key` — ключ спортивного события, если доступен;
- `market_kind` — контролируемый тип, например `match_winner` или `map_winner`;
- `period` — идентификатор периода (`match`, номер карты/сета и т. п.); отсутствие значения не означает wildcard;
- `outcomes` — ровно два исхода с PM token IDs и каноническими participant/entity labels;
- `start_at` — необязательное время начала для контекстного matching, а не единственное доказательство совпадения;
- `event_url` — только обычная HTTPS-страница события Polymarket.

### Binding

Binding — отдельная привязка пары `(adapter_id, PM market_key)` к одному событию и одному bookmaker market. Целевое содержимое:

- `adapter_id` и устойчивый `provider_event_id`;
- `provider_market_id` и точный `market_kind`/`period`;
- отображение каждого из двух PM outcomes в разные bookmaker outcome IDs (явный `swap` допустим только как сохранённый результат строгого matching);
- `match_status` и диагностические доказательства/причина, score и margin при их наличии;
- `bound_at` и ревизия каталога, чтобы можно было отбрасывать binding к исчезнувшему объекту;
- нормализованный `event_url`, если адаптер умеет построить безопасную обычную страницу.

Пустой либо неоднозначный binding не публикуется как успешный результат. Binding одного adapter не переиспользуется как цена другого.

### Quote snapshot

Для каждой bookmaker стороны адаптер отдаёт snapshot с:

- `adapter_id`, `provider_event_id`, `provider_market_id`, `outcome_id`;
- `price` — конечный коэффициент decimal odds в исходном формате источника;
- `state` — как минимум открыта/закрыта/приостановлена/неизвестна;
- `received_at_monotonic` для расчёта возраста внутри процесса и `received_at_epoch` для диагностики/передачи наружу;
- необязательный `provider_timestamp` с пометкой, что он получен от источника;
- необязательные `raw_market_name`/`raw_outcome_name` для диагностики, но не для повторного fuzzy-match в UI.

Адаптер не выставляет самостоятельно «свежесть» без предоставления receipt time и TTL. На границе с текущим scanner contract snapshot может быть преобразован в legacy quote `{src, o, c, age_sec}`; внутренний контракт должен сохранять источник и время получения без округления.

## Интерфейс адаптера

Целевой интерфейс (названия методов уточняются при реализации):

- `adapter_id` и read-only capabilities;
- `start()` / `stop()` — владение transport threads/tasks и их корректное закрытие;
- `wait_ready(timeout)` — readiness каталога/транспорта; timeout не должен блокировать scanner навсегда;
- `bind(pm_market) -> Binding | None` — строгая привязка, без сетевого действия ставки;
- `get_quote_pair(binding) -> QuotePair | None` — атомарная выдача двух исходов одного bookmaker market;
- `set_update_callback(callback)` — уведомление об изменении provider event ID, без передачи тяжёлого полного каталога;
- `health() -> AdapterHealth` — состояние транспорта, каталога, времени последнего сообщения/валидной цены, свежих/устаревших quote counts и безопасный тип ошибки.

Реализация может временно сохранять существующие модульные фасады `get_global_stream()`, `bind_slug()`, `get_live_bc()`, `wait_ready()` и `stop_global_stream()`. Совместимость фасада предпочтительнее одномоментной миграции потребителей.

## Контракт обновления и индексы

Обновление передаётся как лёгкое событие `(adapter_id, provider_event_id, received_at_monotonic)`; PM CLOB update использует `(pm, token_id, received_at_monotonic)`. Очередь coalesce-ит повторные обновления одного источника/идентификатора и ограничивает размер/drain работы.

Для разрешения event → recalculation целевые обратные индексы:

- `pm_token_id -> set[market_key]`;
- `(adapter_id, provider_event_id) -> set[market_key]`.

Индексы строятся из активных рынков и актуальных binding. При полной/частичной reconciliation каталога правила сохранения старого PM catalog остаются прежними; удалённый рынок убирается из индексов только тогда, когда удаление подтверждено успешной reconciliation. При смене enabled adapters, перепривязке события или смене provider market затронутые ключи перестраиваются атомарно, а изменившиеся рынки помечаются dirty. Устаревшие события со старой ревизией binding игнорируются.

Dispatcher объединяет dirty market keys, затем последовательно вызывает текущий production расчёт и публикует согласованный snapshot. Периодические проверки свежести и bounded fallback polling допустимы как страховка, но не заменяют event path адаптера, если адаптер поддерживает callback.

## Routing нескольких источников

Каждый активный adapter строит независимую привязку к PM market. На этапе расчёта выбирается один источник по явной политике приоритета/fallback; обе ноги bookmaker не объединяются и котировки разных адаптеров не смешиваются. Если primary временно не даёт пригодную полную пару, fallback можно использовать только как самостоятельную пару Polymarket ↔ fallback adapter, с собственным source label, binding и диагностикой. Приоритет и fallback не должны скрывать фактический источник в UI/status.

При отключении адаптера его binding, обратные индексы и ожидающие callback события инвалидируются. После включения выполняются bind и пересчёт затронутых рынков; прежняя цена отключённого источника не остаётся активной.

## Диагностика и безопасная ссылка

Health должен различать transport connected/readiness, completeness каталога, число обнаруженных и привязанных событий, число свежих пар, возраст последнего transport message и последней валидной цены, TTL и код последней ошибки. Секреты, cookies, account IDs и сырые auth payload не включаются.

`event_url` валидируется на границе источника: HTTPS, разрешённый origin из конфигурации адаптера, обычный маршрут события. Query/path с купоном, stake или account operation запрещены. UI открывает ссылку вручную; адаптер не вызывает browser automation и не выполняет операцию на странице.

## Текущее состояние и план без смены поведения

- `bk_router.py` сейчас отвечает за 1win-first/BetBoom fallback, runtime source selection, binding cache и feed health. Публичный контракт у источников пока различается.
- `onewin_bridge.py` имеет event callback с match ID; fresh pair строится из ровно двух открытых котировок и TTL от локального `receivedAt`.
- `event_dispatch.py` coalesce-ит `pm` token ID и `1win` match ID; `polyarb_v4.py` строит PM token index и OneWin match index.
- BetBoom пока не включён в тот же callback/index path; для некоторых его расчётов сохраняется ограниченный polling. Health router сейчас экспортирует health 1win.
- Существующие fail-closed matching, source routing, score thresholds и fallback поведение не ослаблять в рамках выделения интерфейса.

Безопасный порядок реализации: (1) добавить протокол/нормализованные dataclasses и тесты на synthetic adapters; (2) адаптировать существующие 1win и BetBoom фасады без изменения их matching; (3) обобщить event ID/обратные индексы и callback routing; (4) проверить включение/отключение, fallback promotion, freshness, partial catalogs и stale events; (5) только отдельным решением оценивать будущие источники. Ни одна стадия этого документа не разрешает подключать новую БК или добавлять действия со ставками.
