# Семантика legacy-полей и заметки по миграции

**Область действия:** поддерживаемый read-only путь сканера `polyarb_v4.py` → snapshot сканера → канонический `web_app.py` → dashboard. Это контракт полей, а не разрешение на размещение ставок. `server/monitor.py` и записи сохранённой истории сделок — отдельные legacy-контексты; нельзя считать, что одноимённые поля в них имеют то же значение, что в snapshot сканера.

## Финансовые поля

| Legacy-поле | Текущее значение | Каноническое соответствие / правило миграции |
|---|---|---|
| Config `bank` / входной `bank` сканера | Настроенный общий банк аккаунта в USDT. Перед расчётом кандидатов сканер применяет `_risk_capped_plan_bank()`. | Не преобразовывать в `calculation.total_stake`; хранить банк/лимит отдельно и называть явно. |
| Snapshot `total_bank` | Общий настроенный банк, переданный сканеру, в USDT. | Это не сумма, вложенная в возможность. Сохранять только как контекст банка/настроек, если он понадобится будущему контракту. |
| Snapshot `bank` | В основном production-сканере — `sum(stakes)` для этой возможности, в USDT. Это значение отличается от config `bank`; отдельный старый/demo producer может использовать это имя иначе. | `calculation.total_stake`; проверять сумму нормализованных ставок ног с документированным допуском. |
| `bets` + `stakes` | Параллельные позиционные массивы: `stakes[i]` — плановое денежное распределение для `bets[i]`. Текущая production-валюта — USDT. | Переносить `stake` внутрь соответствующей ноги. При переходной нормализации не считать, что индекс 0 всегда соответствует определённому источнику; связывать элементы по идентичности ноги. |
| `bets[].s` | Параметр slippage, используемый в `eff_mult`; это не ставка. | Не переносить в `legs[].stake`. |
| `bets[].c` | Доля комиссии или аналогичный коэффициент, используемый в `eff_mult`; это не ставка и не цена. | Сохранять как вход расчётной модели только при явном добавлении model-specific metadata. |
| `bets[].o` | Типозависимый эффективный десятичный множитель. Для ноги букмекера это десятичный коэффициент букмекера. Для Polymarket это похожий на коэффициент множитель с учётом комиссии, а не вероятность, исходная цена ask или букмекерская котировка. `compute()` применяет `eff_mult(o,c,s)` и рассчитывает пропорциональное распределение, выплату, прибыль и ROI. | Не переносить напрямую в `legs[].price`. Для PM использовать типизированную цену котировки и отдельно хранить предположения о комиссии/модели. Не учитывать комиссию PM дважды. |
| Snapshot `payout` | Моделируемая общая валовая выплата, возвращаемая расчётом распределения сканера, в той же валюте, что и ставка возможности. | Это не чистая прибыль и не фактически исполненная/рассчитанная выплата. Сейчас это необязательное поле Opportunity v1. |
| Snapshot `profit` | `payout - bank` после расчёта/refinement сканера; прогнозируемая чистая прибыль моделируемой пары, в той же валюте, что и `bank`. | `calculation.projected_profit`; это оценка до исполнения, не реализованный P&L и не гарантия исполнения. В истории сделок `profit` также используется для расчёта, внесённого пользователем; эти контексты нужно разделять. |
| Snapshot `roi` | Безразмерная доля сканера: `1 / sum(1 / effective_multiplier_i) - 1`; при согласованном расчёте равна `profit / bank`. Значение `0.04` означает 4%. | `calculation.roi_fraction`; переводить в проценты только при отображении. Перед отклонением записей с несовпадением `roi` и `profit / total_stake` нужно определить явный допуск. Исторический совокупный ROI рассчитывается отдельно как `sum(profit) / sum(bank)`. |
| Snapshot `ts` | Unix epoch в секундах, зафиксированный сканером при создании snapshot кандидата; это не timestamp котировки от поставщика. Возраст котировок фиксируется раньше, при построении кандидатов, поэтому абсолютное время `ts - age` приблизительно из-за времени на refinement и сериализацию. | Считать временем расчёта кандидата (`computed_at`), не временем наблюдения у поставщика. Текущий `timestamp_basis=received_at` означает возраст, выведенный из локального времени получения, а не нативный timestamp поставщика. |
| Backend `first_seen_ts` / `age_sec` | Локальное время backend, когда он впервые увидел slug, и прошедшее с этого момента время; это не возраст любой из котировок. Значение может сохраняться между повторными snapshot с тем же slug. | Использовать только как метаданные отображения/жизненного цикла. Не применять для freshness котировок или `legs[].age_ms`. |
| Snapshot `pm_age` / `pm_book_age_sec`; leg `odds_age_sec` / root `bk_odds_age_sec` | Возраст PM — время с последнего изменения локального стакана (с fallback-механизмом); возраст котировки букмекера предоставляет адаптер источника. Root-поля snapshot дублируют значения соответствующих ног для старых потребителей. Ни одно из них не является абсолютным timestamp поставщика. | Считать длительностями для конкретных источников. Поля возраста PM в leg имеют приоритет над root PM age; `odds_age_sec` ноги букмекера — над root `bk_odds_age_sec`. Отсутствующий возраст означает неизвестное значение, а не ноль. |
| 1win `odds_age_sec` / `bk_odds_age_sec` | `OneWinStream` записывает локальный `time.time()` в `receivedAt` конкретного коэффициента, когда обновление feed содержит конечную цену `cf`; `age_sec` — локальное текущее время минус это время получения. Timestamp поставщика из сообщения не используется для freshness. Повторное сообщение с валидной ценой обновляет возраст получения, даже если числовая цена не изменилась; delta только со статусом/именем сохраняет прежнее время получения цены. Используются только открытые котировки возрастом не больше `ONEWIN_MAX_ODDS_AGE_SECONDS` (по умолчанию 30 секунд; значение настраивается). | Это свежесть по времени получения feed, а не доказательство того, когда 1win изменил или сформировал котировку. Не указывать время поставщика, пока нет отдельно подтверждённого контракта timestamp. |
| Backend `source_age_sec` / `source_state` | Legacy-индикатор общей свежести, который `web_app.py` рассчитывает как максимум возраста snapshot и возраста букмекерской котировки (или только возраста букмекерской котировки, если `ts` snapshot отсутствует). Возраст PM-стакана **не учитывается**. `source_state` принимает `fresh`, `stale` или `unknown` согласно порогу backend. | Не использовать этот агрегат вместо свежести каждой ноги. Opportunity v1 вычисляет статус по возрасту обеих ног; при dual-read индикаторы могут обоснованно расходиться, особенно если PM-стакан старше букмекерской котировки. |
| `phase` / `is_live` | `phase` имеет три состояния: `live`, `prematch`, `unknown`. `is_live` — legacy boolean-проекция `phase == live`; одно значение `false` не различает подтверждённый прематч и неизвестную фазу. | Использовать нормализованный `phase`; не выводить `prematch` только из `is_live=false`. |

## Котировки Polymarket

| Legacy-поле | Текущее значение | Правило миграции |
|---|---|---|
| `pm_best_ask` / `pm_best_bid` | Лучшая цена ask/bid верхнего уровня стакана для одного PM token, в единицах вероятности/USDT за долю в диапазоне `[0,1]`; не в центах. | Хранить отдельно от цены, учитывающей глубину. UI может показывать центы, умножая значение на 100. |
| `pm_avg_ask` | Средняя цена, полученная проходом по глубине стакана через `walk_book()` для исходного размера probe `pm_target_shares`, в тех же единицах, что и best ask. Это не простое среднее цен уровней. | Сохранять как метаданные исходного probe; не подменять молча ценой best ask. |
| `pm_refined_avg_ask`, `pm_refined_shares`, `pm_refined_stake_usd` | Аддитивные поля, записываемые `refine_stakes()` для прохода по глубине, размер которого рассчитан от распределённой ставки: цена PM, размер прохода в долях и распределение PM, использованное как вход для определения размера. `pm_refined_shares` рассчитывается как allocation / best ask; это read-only оценка, не ордер и не исполнение. | Opportunity adapter предпочитает refined VWAP, если цена и размер долей валидны; он указывает `price_basis=depth_average` и `price_size_shares`. В старых snapshot используется fallback: исходный `pm_avg_ask` + `pm_target_shares`, затем best ask с `price_basis=top_of_book`. |
| `pm_target_usd` | Размер исходного probe: по умолчанию 50 USDT; при положительном плановом банке сканера — половина этой суммы, ограниченная диапазоном 20–200 USDT. Используется для первоначального прохода по глубине стакана. | Информационные метаданные размера, не обязательно совпадающие с итоговой ставкой PM. |
| `pm_target_shares` | Доли исходного probe, рассчитанные как `pm_target_usd / pm_best_ask`. Это оценка количества долей, не USD, не ордер, не исполнение и не гарантия доступного размера. Не учитывает модель комиссии. | Не смешивать с итоговой ставкой ноги и фактически исполненным количеством долей. Потребителям следует пересчитывать размер по текущему стакану и выбранной сумме. |
| `pm_age` / `pm_book_age_sec` | Секунды с последнего изменения локального стакана PM (с fallback-механизмом), не абсолютное время и не возраст всей возможности. Producer записывает оба имени в PM leg и дублирует `pm_age` в корне snapshot. | Нормализовать в одну длительность в порядке: leg `pm_book_age_sec`, затем leg `pm_age`, затем root `pm_age`; не трактовать как время события у поставщика. |

### Границы цены и расчёта PM перед дальнейшей миграцией UI

`build_arb_candidates()` сохраняет исходный `pm_avg_ask`/probe. `refine_stakes()` аддитивно публикует `pm_refined_avg_ask`, `pm_refined_shares` и `pm_refined_stake_usd` для прохода по глубине, рассчитанного от распределённой ставки; Opportunity v1 предпочитает refined-значение и указывает его размерную основу, а старые snapshot используют исходный probe как fallback. Multi-level-book regression подтверждает, что исходный probe и refined size различаются, а исходные legacy-поля остаются неизменными. Если за пять итераций значения не стабилизируются, сканер отклоняет кандидата; при стабилизации котировка и возвращённое распределение относятся к одной последней итерации в пределах действующего допуска сходимости. Котировка остаётся read-only оценкой, а не гарантией исполнения.

## Ссылки на события

- Legacy `bk_event_url` — ссылка уровня snapshot на страницу события букмекера. Для 1win она берётся из нативного `event_url` соответствующей source binding; для BetBoom UI в основном строит адрес из BetBoom match ID и tournament ID.
- `pm_event_url` — ссылка на market event Polymarket, построенная по slug рынка. `/api/pm_url/{slug}` — fallback-builder для того же адреса.
- Эти ссылки не взаимозаменяемы. В канонической модели ссылка принадлежит конкретной ноге (`legs[].event_url`), а не рынку как нетипизированная глобальная ссылка. Если ссылка источника отсутствует, она должна оставаться пустой — нельзя подставлять ссылку другой ноги. Перед открытием действие должно выбрать ногу по `source` и проверить HTTPS и точное разрешённое origin этого поставщика.
- Сейчас dashboard проверяет 1win относительно настроенного origin; прямой и fallback-адреса Polymarket проходят общую проверку точного origin/path `https://polymarket.com`. Helper отвергает credentials, не-HTTPS, поддомены, похожие суффиксы, нестандартные порты и пути вне `/event/`; regression-тесты запускаются в Node/CI. Построение маршрута BetBoom по ID — отдельное source-specific правило.

## Безопасный порядок миграции

1. Оставить `web_app.py` каноническим backend и сохранить текущую dual-read границу карточки: детали, калькулятор, фильтры, ссылки/действия, закреплённые snapshot и история пока остаются на legacy-данных.
2. Описания схемы и replay assertion уже закрепляют сумму/порядок ставок, единицы ROI и различие PM top ask и depth average; до смены источника расчётов добавить явный replay комиссии PM и effective multiplier на многоуровневом стакане.
3. Аддитивные PM depth price/size metadata, multi-level-book regression и fail-closed поведение при несходимости уже добавлены. До миграции расчётов добавить captured replay-кейсы, проверяющие комиссию PM/effective multiplier и согласованность расчёта.
4. Opportunity v1 переносит legacy PM/bookmaker URL в соответствующие ноги; browser-тесты доказывают, что текущие legacy-backed действия открывают ссылку нужного источника. Проверка allowlist для прямых и fallback-ссылок PM покрыта `tests/test_provider_links.cjs`. Переключать чтение действий на v1 можно только после обновления тестов: они должны напрямую проверять v1 URL и сохранять legacy fallback.
5. Только после этого рассматривать перенос расчётов или действий на Opportunity v1; read-only поведение должно сохраняться на всём протяжении миграции.
